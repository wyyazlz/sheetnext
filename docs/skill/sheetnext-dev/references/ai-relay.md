# AI Request Contract

> Maintained in `docs/static-references/ai-relay.md`; copied into the skill by `scripts/doc-scanner.js`. See `core-api.md` for the matching source version and fingerprint.

## Purpose

This document describes the request data built by the SheetNext front end and the response format that the configured `AI_URL` endpoint must accept.

It does not define your internal server implementation.

The exact client behavior is based on `src/core/AI/AI.js`.

The built-in AI runtime requires the commercial distribution and its applicable license. Open Edition does not include this runtime.

## Security And Execution Boundary

`Query` and `Edit` execute model-supplied JavaScript with `new Function` / `eval` in the host page. They are not sandboxed. The `Query` description requests read-only behavior but does not enforce it; `Ask` is a model-selected tool, not a mandatory approval gate for every edit.

- Use a trusted HTTPS relay. Keep model-provider keys on that server. `AI_TOKEN` is a browser-visible application token, not a place for a provider key or a permanent backend secret; issue short-lived tokens with the required scope.
- Authenticate the user and authorize workbook access on the server. Validate request size, message structure and supported tool schemas against the deployed client version; reject unknown tools and bound token usage, concurrency and rate limits.
- Treat client messages, tool definitions and `isUserStart` as untrusted request data. They must not determine user identity, billing entitlement or access to server tools. Preserve supported message structure only after validation.
- Workbook context, attachments and screenshots can be sent to the relay and onward to the model provider. Apply the application's data-access and retention rules before enabling this flow.
- Arbitrary code can access page globals and same-origin resources. Use an isolated origin with a narrow, validated message bridge, or replace code execution with constrained operations before enabling this runtime alongside sensitive host-page capabilities. A tool-name allowlist or prompt instruction cannot make arbitrary JavaScript safe.
- A strict CSP that disallows dynamic code evaluation is incompatible with the current Query/Edit implementation. Decide the execution architecture explicitly; do not automatically relax the host application's CSP to make an example work.

## Client Configuration

Configure the AI endpoint when creating `SheetNext`:

```js
const SN = new SheetNext(container, {
  AI_URL: 'https://your-server.example.com/api/ai',
  AI_TOKEN: applicationSessionToken
})
```

- `AI_URL`: required if you want to use the built-in AI runtime
- `AI_TOKEN`: optional; when present, the browser sends `Authorization: Bearer <token>`

`applicationSessionToken` is obtained from your authenticated application backend. Configure relay authentication even when the optional token field is omitted; the client does not enforce server access control.

## What the Front End Sends

The front end sends an HTTP `POST` request to `AI_URL` with:

- `Content-Type: application/json`
- optional `Authorization: Bearer <token>`

Request body:

```json
{
  "messages": [
    {
      "role": "system",
      "content": "System prompt text"
    },
    {
      "role": "user",
      "content": "User instruction"
    }
  ],
  "tools": [
    {
      "type": "function",
      "function": {
        "name": "View",
        "description": "Capture a sheet area",
        "parameters": {
          "type": "object",
          "properties": {
            "cellRef": { "type": "string" }
          },
          "required": ["cellRef"]
        }
      }
    }
  ],
  "isUserStart": true
}
```

## Request Field Meaning

### `messages`

This is the main Chat Completions-style message array built by the client.

The front end assembles it from:

- a system prompt
- previous conversation history
- optional attachment messages
- a final system snapshot describing current workbook context

Each message uses the usual chat structure:

```json
{
  "role": "user",
  "content": "plain text"
}
```

For attachment cases, `content` can also be an array of parts:

```json
{
  "role": "user",
  "content": [
    {
      "type": "text",
      "text": "User uploaded attachments:"
    },
    {
      "type": "image_url",
      "image_url": {
        "url": "data:image/png;base64,..."
      }
    }
  ]
}
```

So from the server perspective:

- preserve supported message roles and tool-call associations after validating the request
- `content` may be either a string or a multimodal content array

### `tools`

This is the built-in tool definition array generated by SheetNext and sent together with the messages.

Validate tool names and parameter schemas against the deployed client version. The current built-in tool names are `View`, `Query`, `Edit` and `Ask`; the example above shows one tool only. Do not add server-side execution privileges merely because the browser supplied a tool definition.

If your model provider supports tool/function calling, forward the validated definitions or map them to your provider's equivalent format. Preserve exact tool names in the response. Returning an invented name such as `setCellValue` will not invoke a built-in tool.

### `isUserStart`

Boolean flag:

- `true`: this request starts a new user turn
- `false`: this request is a follow-up turn in the current workflow

The front end sends it for server-side flow control if needed. It is client-controlled and must not serve as an authorization or billing decision by itself.

## What the Server Must Accept

At minimum, the configured `AI_URL` endpoint should accept:

```json
{
  "messages": "Chat Completions-style message array",
  "tools": "SheetNext tool definitions",
  "isUserStart": true
}
```

In practical terms:

- `messages`: required
- `tools`: required by the current client contract
- `isUserStart`: required by the current client contract

## What the Front End Accepts Back

The current client expects a streaming response and parses it as SSE-style `data:` lines.

Recommended response header:

```text
Content-Type: text/event-stream
```

Stream example:

```text
data: {"type":"text","delta":"Hello"}

data: {"type":"text","delta":" world"}

data: [DONE]
```

Each event should be one `data: ...` line followed by a blank line.

Disable response buffering in the reverse proxy and flush complete SSE events as they are produced. Propagate browser disconnects to cancel the provider request where possible. Raw provider SSE is not necessarily compatible with these normalized chunks.

## Supported Response Chunks

### `text`

Append assistant text to the UI.

```json
{
  "type": "text",
  "delta": "Hello"
}
```

### `tool_call`

Incrementally stream a tool call. `arguments` may be partial.

```json
{
  "type": "tool_call",
  "tool_call": {
    "index": 0,
    "id": "call_1",
    "type": "function",
    "function": {
      "name": "View",
      "arguments": "{\"cellRef\":\"A1\""
    }
  }
}
```

### `tool_call_complete`

Provide the completed tool call payload.

```json
{
  "type": "tool_call_complete",
  "tool_call": {
    "index": 0,
    "id": "call_1",
    "type": "function",
    "function": {
      "name": "View",
      "arguments": "{\"cellRef\":\"A1\"}"
    }
  }
}
```

### `usage`

Optional usage information.

```json
{
  "type": "usage",
  "usage": {
    "input_tokens": 1200,
    "output_tokens": 260,
    "total_tokens": 1460
  }
}
```

### `web_search`

Optional status chunk recognized by the current client.

```json
{
  "type": "web_search",
  "status": "in_progress"
}
```

or:

```json
{
  "type": "web_search",
  "status": "completed"
}
```

### `error`

Structured stream error.

```json
{
  "error": {
    "message": "Model request failed"
  }
}
```

## Error Handling

- non-2xx HTTP responses are treated as request failures
- a 2xx response can still fail by streaming an `error` payload
- plain text or HTML error bodies are shown as error content
- unknown chunk types are ignored by the current client

## Recommended Server Strategy

The simplest integration is:

1. authenticate the request and enforce workbook access, size and usage limits
2. validate `messages`, `tools`, and `isUserStart` against the deployed client contract
3. call your model service
4. convert the model output into the SSE chunk format above
5. stream it back to the browser

This describes protocol compatibility. Apply the execution boundary above separately; a compatible relay is not itself a sandbox for generated code.
